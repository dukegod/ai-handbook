# 跨角色交付：产品、业务、研发能否在同一平台协作

> **TL;DR**：方向成立，但「大家在一个平台上交付」这个说法会误导。**统一的是上下文和验收，不是动作。** 现阶段是"需求到代码的翻译层被压缩了"，不是"多角色合流到一个交付流"。

⏱ 预计阅读时间：7 分钟

## 你能在这里学到

- 厂商在这条路上最激进的主张是什么
- 已经成立的部分：上下文统一
- 还没成立的部分：动作统一
- 真正的瓶颈在哪（不是工具层）
- 一个能自己跑的最小验证实验

## 一、厂商的主张：Cursor 最激进

Cursor 已经开了 `cursor.com/for/product-managers` 页面，官方措辞是：

> PMs use Cursor to prototype features, validate concepts with working code, and ship small changes directly.

给 PM 的能力边界写得很清楚：**做原型、直接查询代码库回答技术问题、生成基于代码实际可能性的 spec、接入 Jira / Notion / Figma**。

Cursor 设计负责人 Ryo Lu（Notion 创始设计师之一）2026-02 那场访谈把这套逻辑说得更根本。他提到过去 Cursor 没有 PM，现在有了，但 PM 也只是做自己擅长的部分——**「所有人在同一个材料上工作，那个材料是代码」**。

他对旧模式的批评是：

> 「PM 写需求文档、组织会议、把东西发出去。设计师做 mock，把别人的概念翻译成像素。工程师接到拆好的小工单，执行完就完了……So all of these people are so disjoint, they all use separate tools, they all talk differently — what the fuck are we doing?」

他的主张是：**大家都是 software builder，只是有人擅长文字、有人擅长像素、有人擅长写代码。** 平台负责把「材料」统一成代码。

## 二、已经成立的部分：上下文统一

这是这条路真正兑现的价值，方向上很明确。

传统链路的信息损耗在于：**PM 写的东西和工程真正要做的事之间有一层翻译**，这层翻译由工程师完成，所以：

- 需求文档里的技术约束，往往到实现时才发现不成立
- PM 无法自己验证"这个想法能不能做"
- 工程师在重复解释同一件事

Cursor 这套工具压缩的正是这一层：**PM 生成的 spec 是基于代码实际可能性的**，不是凭空写的。工程师不需要再给 PM 解释技术边界——PM 直接在边界里写 spec。

**这是真实且具体的收益，不是叙事。** 如果你的团队里 PM 经常问"这个能不能做"，这条价值立刻可感知。

## 三、还没成立的部分：动作统一

看 Cursor 给 PM 的实际能力：prototype、query、spec、接 Jira/Notion。

**PM 交付的是一个可运行的原型和一份 plan。代码还是工程师审、工程师合。** PM 没有获得"直接上线"的能力。

所以现阶段更准确的说法是：**需求到代码的翻译层被压缩了，发布链路没变。** 这跟"多角色合流到一个交付流"是两件事。

一个侧面佐证：Cursor 的 self-testing agents 让 agent 自测到通过才提 PR，artifacts（视频 / 截图 / 日志）替代 diff 给非工程角色看。这套东西如果成为主流，**"看懂代码 diff"就不再是研发的专利**——但注意，它替代的是**验收**，不是**提交动作**。

## 四、真正的瓶颈不在工具层

Ryo Lu 在同一场访谈里给了一个关键数字：

> **最强的程序员同时也只能管理约 4 个 agent，人类正在成为 AI 协作的瓶颈。**

这句话反过来读很重要——**非工程角色能同时管几个 agent？1 个？2 个？**

没有厂商公布过这个数字。但可以推断：PM 的调度带宽大概率显著低于资深工程师。**如果一个角色只能同时盯 1-2 个 agent，"统一平台"带来的不是产能扩张，反而可能是协作复杂度的上升**——因为所有人都在同一份材料上，但没有人有余力在上面做深度判断。

**平台统一了上下文和验收，但人的调度带宽没统一。** 这是我认为这件事目前最大的隐性成本。

还有一个组织层面的前提要说清楚：Cursor 说自己设计团队只有 4 人、"几乎所有工程师也在做设计"、过去没有 PM 也能运转。**可核实的是这个团队的规模本身**——它确实小到不需要角色分工。

但「所有人都在同一材料上工作」能否外推到别的规模，**没有任何公开数据支撑**。Cursor 是用自己的组织结构去论证产品设计，这在小团队里成立，在有 PMO、有流程、有合规约束的成熟组织里需要额外机制才能落地。本页不对"多大规模开始失效"给数字——那需要你自己团队的数据来测。

## 五、我的判断：终态不是"一个平台"

更可验证的说法是：

> **同一个平台上，不同角色交出不同性质的产物（PM 交可运行原型、设计交可交互界面、研发交可合并 PR），但共享同一份上下文和同一条验收链路。平台统一的是上下文和验收，不是动作。**

这个说法的好处是可以被证伪。哪些地方统一了、哪些没统一，都能看到。而"大家在一个平台上交付"这个说法没法验证——它听起来对，做不到也说不清哪里不对。

另外补一个反向数据：Anthropic 披露的 Cowork 用量里，软件开发只占 8.7%，真正的大头是商业流程（33.4%）和内容创作（16.4%）。这说明**"研发平台变成全公司交付平台"这个跃迁，连最激进的厂商都还没走完**——研发工具向非研发角色扩张是确定方向，但非研发角色的主要工作恰恰不在"交付软件"这条线上。

> ⚠️ 这组数据来自第三方报道转述的 Anthropic 自披露统计，我未核到原始报告。属于自披露数据，不是独立第三方测量。

## 六、验证方法：最小实验

想验证这判断在你的团队成不成立，别看厂商 benchmark，做个小实验：

```
1. 挑一个真实的、边界清晰的小需求（不要用大需求试）
2. 让 PM 用 Cursor 的 Plan Mode 直接出 plan
3. 你（研发）只做一件事：审阅 plan 的质量
4. 跳过中间的 spec 文档撰写 + 需求评审会
5. 跑 3 个需求后对比
```

**要测的数**：省下的沟通成本 vs 增加的 plan 审阅成本。

- 沟通成本 ≈ 传统链路里"PM 写文档 + 评审会 + 研发解释边界"的时间
- 审阅成本 ≈ 审 plan 的时间 + plan 质量不过关时的返工

**如果省下的沟通成本明显大于审阅成本**，这条路在你的团队成立——说明翻译层压缩的收益是真实的。**如果几乎持平**，那说明你的组织瓶颈不在信息传递层，工具再统一也帮不上忙。

这个数据比任何厂商的 benchmark 都有说服力，因为它测的是你的组织，不是别人的。

## 七、三个继续观察的指标

1. **PM 能不能独立 merge**——两年后如果 PM 还是只能交 prototype，融合就停在工具层；如果厂商往企业侧开了"PM 直接发布"，才是真的合流
2. **验收链路是否统一**——self-testing + artifacts 是否成为主流验收方式，决定"看懂 diff"会不会变成历史
3. **非工程角色的 agent 调度上限**——Ryo 说的"最强程序员管 4 个"，这个数字在 PM 身上是几？至今没人公布过
