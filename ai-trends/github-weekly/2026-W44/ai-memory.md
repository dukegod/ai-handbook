# akitaonrails/ai-memory：让 20 多个 Agent 共用一份记忆，交接是有归属的协议

> **TL;DR**：README 第一句就把场景讲清楚了——**在 Claude Code 里干到一半退出，在同一目录打开 Codex，不用重新解释架构、失败的尝试和悬而未决的问题**。但真正的设计不在「记住」，而在**交接被定义成一个有归属、且恰好被认领一次的类型化协议**。真相源是 git 管理的 markdown，默认路径零 LLM 调用。本周涨星 +3,254，占存量 24%。

## 是什么

[akitaonrails/ai-memory](https://github.com/akitaonrails/ai-memory) 是用 Rust 写的 **Agent 长期记忆服务**（MIT，官网 aimemory.sh，要求 Rust 1.95+）。它针对的是各家 Agent 自带记忆的共同短板：**笔记只活在一台机器上、只属于一个 Agent、一换工具就消失、交给同事就断档**。

四个「跟着你走」：

1. **跨 Agent** —— 20 多个 harness（Claude Code、Codex、Cursor、OpenCode 等）向同一份记忆供给。
2. **跨项目** —— 一份关于「你通常怎么干活」的小档案（包管理器、测试布局、架构习惯）在新仓库会话启动时就到位，**位置在各仓库规则文件之下，作为默认值**。
3. **跨机器** —— 记忆住在你自己跑的服务里，笔记本、homelab 或别处都行。
4. **跨团队** —— 所有人都指向同一个服务，一个人的会话所学可以被所有人的 Agent 检索；**知识按项目共享，个人交接保持个人**。

## 技术亮点

**第一，交接是类型化协议，不是相似度检索。** README 写得很明确：*each one has an owner and is claimed exactly once*——每条交接都有归属，且恰好被认领一次。**这把记忆问题从「检索问题」重新定义成了「状态机问题」**：要解决的不是「哪段文本和当前任务语义相关」，而是「谁在接这件事、接了没有、有没有半途而废」。这个转换是项目最有价值的部分。

**第二，它能带过来的是「会话」而不只是「摘要」。** 用 `ai-memory run` 启动时，Codex 拿到共享工作流，外加 Claude 可见原生历史的一份**私有临时本地投影**，补齐启动包因长度限制省略的细节。关键在隐私边界：**远端服务只收到 harness 与会话身份，永远收不到本地 transcript 的路径或内容**。

**第三，记忆是普通 markdown，数据库只是可重建的索引。** 真相源是一个 git 支撑的 `.md` wiki：可以 grep、可以用 Obsidian 打开、可以手改。**索引永远能从文件重建，没有向量库要维护，内容也没有被锁进二进制**。对已经在用 wiki 的团队迁移成本几乎为零，而且天然可审计。

**第四，默认路径零 LLM 调用。** 生命周期 hook 记录发生了什么（提示词、工具调用、会话边界），在**类型化的隐私边界**上净化后落库，服务端整合成可读页面。捕获、检索、交接都不需要 API key。**记忆衰减也不需要 LLM**：按层级设定衰减节奏，被用过的衰减更慢（打开、搜索、经链接到达都算使用），情节性笔记变冷时可压缩成耐久事实（路径、错误码、决策），近重复会合并、疑似矛盾会被标记——**零 API 调用，且没有任何东西被硬删除**（原件留在 git 和版本链里）。

## 后续发展建议

**它提供的不是「更好的向量库」，而是三条可以搬到内部平台的机制。**

- **类型化交接协议值得直接抄。** 内部平台做「任务在多个 Agent 之间流转」时，**交接单必须有归属、有认领状态、有唯一性约束**——这三条是状态机的基本盘，也是最容易漏的部分。「把上下文摘要塞进 prompt」没有归属概念，结果就是同一个任务被多个 Agent 同时推进、或者谁都以为别人做了。**建议交接数据结构至少含：归属者、认领状态、待解决事项、证据路径。**
- **纯 markdown 真相源 + 可重建索引，是企业内部场景的正确答案。** 内部知识资产需要被审计方以普通工具打开，而不是只能通过平台 UI。**建议内部记忆层保持文件形态、git 托管，数据库只做缓存**——既有性能，也有可移交性。
- **零 LLM 的捕获与衰减路径，是成本可控的前提。** 多数记忆系统的成本大头是「每次会话都要调 LLM 总结、判重、判断是否过期」。**把判重、压缩、衰减做成确定性规则，LLM 只在真正需要重新理解语义时介入**——这对内部平台的成本模型影响很大，值得作为选型硬指标。
- **隐私边界的设计值得单独学。** 「本地 transcript 不出机、远端只收身份」这种按数据类别切分边界的做法，比笼统的「敏感信息脱敏」更可审计——**脱敏是规则，边界是结构**。内部平台跨信任边界集成时，建议把数据流分成「必须出界的标识」与「绝不出界的原文」。

**风险与局限**：Rust 二进制 + 自建服务，运维门槛比装个 npm 包高；15 个 open issue 配 13,555 star，说明多数用户还没真正接入；「跨厂商交接」依赖各 harness 的 lifecycle hook 能力，**覆盖度 README 未给量化**；另外「知识按项目共享、个人交接保持私有」这条隔离线只描述行为、没说明强制机制，跨团队部署前需重点确认。
