# paperclipai/paperclip：把 Agent 当员工，给它们配预算、审批和审计

> **TL;DR**：README 有一句很能说明定位的话——**如果 OpenClaw 是员工，Paperclip 就是公司**。它是一个 Node.js 服务 + React 界面，用来编排一支 Agent 团队去经营业务：定目标、招人（任何 bot、任何 provider）、审策略、设预算、开工。本月涨星 +24,081，涨星占存量 22%。

📅 数据窗口：2026-10-20 ~ 2026-10-26 ｜ 🏷️ Agent 组织治理 ｜ 本月涨星 +24,081 ｜ 总 star 107,349

## 是什么

[paperclipai/paperclip](https://github.com/paperclipai/paperclip)（MIT，TypeScript，官网 paperclip.ing）是**面向团队的 Agent 编排开源项目**。自述是「人们用来管理工作 Agent 的应用」，形态像个任务管理器，底下是组织架构、预算、治理、目标对齐和 Agent 协作。

核心流程三步，标题是 **Manage business goals, not pull requests**：

1. **定义目标** —— 比如「把 AI 笔记应用做到 100 万美元 MRR」。
2. **组建团队** —— CEO、CTO、工程师、设计师、市场，任意 bot、任意 provider。
3. **审批并开工** —— 审策略、设预算、按下 go，从看板监控。

支持的执行体包括 OpenClaw、Claude Code、Codex、Cursor + Cloud、Gemini CLI、OpenCode、Pi、Hermes + Gateway、Grok Build、Kimi Code，以及自定义流程、HTTP 端点和外部适配器包。

README 列的适用场景里有一条特别具体：**「你有 20 个同时开着的 Claude Code 终端，然后彻底搞不清谁在干什么」**。这点了出真实痛点——不是 Agent 不够强，是**多 Agent 缺乏可见性与治理**。

## 技术亮点

**第一，「员工 / 公司」这个隐喻选得很准，因为它自带一套成熟的心智模型。** 招人、分工、审批、预算、绩效、审计——企业管理者不需要学新概念。**内部平台落地的最大阻力不是技术能力，而是使用门槛**；把复杂能力包装进已有心智模型，是降低门槛最省力的方式。

**第二，执行层可插拔、治理层统一，这条边界划得清楚。** README 明确：**每个 Agent 可以单独选模型和选 harness，但团队的 tasks、skills、permissions 和 history 统一在一处**。这正是企业内部 Agent 平台最典型的形态——**底下换引擎，上面管资产和权限**。这条边界如果一开始就没划清，后面所有治理能力都会渗进执行层，替换成本会指数上升。

**第三，「能收到心跳就能被雇」的适配契约。** README 那句 *If it can receive a heartbeat, it's hired* 背后是一个最小适配协议：**只要能接收心跳信号就能纳入编排**，适配成本从 O(N)（每个 Agent 一套集成）降到 O(1)。**前提是心跳协议要足以表达生命周期**——开始、进展、阻塞、结束、失败，这是契约设计的真正难点。

**第四，预算、治理、审计是内建能力而非事后补。** README 把「监控成本并强制预算」「让 Agent 24/7 自治但仍能审计工作、必要时插话」列为产品目标。**在企业场景里，这三件套是准入项而非加分项**——尤其「强制预算」，它是把 Agent 从「个人玩具」变成「可运营资源」的分界线。

**第五，任务、skills、permissions、history 四件套放在同一层级。** 这意味着**「这个 Agent 能做什么」和「这团队积累了什么」是同一类资产**，不是两个割裂的子系统。对内部平台来说，这个合并动作的价值可能高于编排界面本身。

## 后续发展建议

**这个项目最适合当内部 Agent 平台的「外部对照样本」——尤其是它的数据模型，而不是它的实现。**

- **「执行层可插拔 + 治理层统一」应该作为内部平台的架构前提写死。** 对应到内部场景：模型可以换、harness 可以换、部署方式可以换，但**权限、审计、技能资产、成本归属这四项必须留在平台层**。**建议在平台设计文档里显式标注「哪一层的东西允许被替换」**——这一条比任何功能列表都重要。
- **「角色 → 技能 → 权限 → 预算」四元组值得作为内部 Agent 的注册模型。** Paperclip 用「招人」隐含了这个结构。**内部平台的 Agent 注册表建议至少包含角色定义、能力清单、权限边界、成本归属四项**，并允许按团队聚合出整体视图。这与 A2A 的 agent card 互补——agent card 描述能力，注册表描述治理归属。
- **心跳契约是最值得借鉴的适配层设计。** 内部平台接异构 Agent 时，**建议先定义一个最小的生命周期事件契约（开始 / 进展 / 阻塞 / 结束 / 失败 + 标识与产物引用），而不是为每种 Agent 写专用集成**。这样新接一个 Agent 的成本就是「适配心跳」，而不是「重写一条集成链」。
- **预算要前置到编排层，不能只在事后统计。** Paperclip 把「设预算」放在「按下 go」之前那一步，这个顺序是对的。**内部平台建议在任务派发时就带上成本上限**，超限行为由平台按策略处理，而不是靠人盯盘。

**风险与局限**：6,595 个 open issue 配 17,836 fork 和 107,349 star，issue 消化压力大，工程成熟度弱于热度；「自主 AI 组织」故事很强，但 README 没给 24/7 自治 Agent 跑真实业务的可靠性证据，内部落地前需要自己的验证数据；技术栈锁死 Node.js + React；商业化（Paperclip Cloud 候补名单）可能影响开源取舍。另外要警惕一个退化——**HR 隐喻容易让项目滑向「只做看板不做实质」**：底层 Agent 的质量、上下文质量、工具可靠性都不在它控制范围内，**组织图画得再漂亮也救不了差模型和烂上下文**。
