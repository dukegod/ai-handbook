# Louis-CFM/coucou：把 Agent 的权限审批做进刘海小组件和手机

> **TL;DR**：Agent 弹权限请求时，如果你人不在电脑前，整个流程就卡住了——**这是 Agent 自治化最现实的摩擦点之一**。Coucou 的解法是把审批入口做成**操作系统级常驻组件**：Mac 刘海里的小圆球（Windows / Linux 是屏幕顶部）、菜单栏、手机端（iPhone / Android，锁屏、动态岛、组件、Siri）。近 30 天新建，累计 6,456 star。

📅 数据窗口：2026-10-20 ~ 2026-10-26 ｜ 🏷️ 人在环内 ｜ 本周未进周榜 ｜ 总 star 6,456（存活 28 天）

## 是什么

[Louis-CFM/coucou](https://github.com/Louis-CFM/coucou)（MIT，Swift 6 + SwiftUI，另有 Tauri 2 组件）是**盯住你 Agent 会话的常驻小助手**：住在 Mac 刘海里（或 Windows / Linux 屏幕顶部），盯着你的 AI 编码 Agent 会话，**现在也在你的手机上**。

能力覆盖：**批准权限、看着 Agent 干活、丢个文件进去、直接和 Claude 聊天**——全程不用离开当前在做的事。离开 Mac 之后它会跟着你到 iPhone：锁屏、动态岛、桌面组件、Siri。

0.4 版本起它还是一个真正的 Mac 应用：按住一个键说话、松手即输入（类似 Wispr Flow），**离线、基于 Parakeet**；还能在不装会议机器人的情况下录通话，产出转录、纪要和待办。平台覆盖 macOS 15+ / iOS 18+ / Android 11+ / Windows 10-11 / Linux。

作者写下了这个项目的动机，很直接：*Some studios showed off gorgeous notch companions… and never let anyone use them. Coucou is the open version.*（有些工作室展示了漂亮的刘海伴侣……然后从不让任何人真的用。Coucou 是开源版本。）

## 技术亮点

**第一，它抓的是一个被反复验证过的需求：审批请求必须能在你当下所在的设备上被处理。** 主流编码 Agent 的权限请求是在终端里弹一个确认框。**人不在机器前 → 流程停住 → 自治程度受限于「人多久没离开电脑」**。消掉这层摩擦，等于放宽了 Agent 能自动跑多远的边界。**这不是小功能，而是把「人机协作带宽」从分钟级拉到小时级。**

**第二，把「人在环内」做成 OS 级常驻，而不是一个 App。** 刘海小组件 + 菜单栏 + 动态岛 + 锁屏 + Siri + 语音输入，共同目标是**把人从「切窗口、切 App」里解放出来**。判断这类入口值不值得做，标准很清楚：**事件是否高频、是否需要打断、是否必须瞬时响应**——权限请求和「任务完成」都满足，所以常驻必需，普通 App 通知不够。

**第三，顺带把语音输入和通话转录收进同一个壳。** 这不是噱头，而是同一个交互模型的延伸：**Agent 相关的事经常需要口头交代**。语音输入（离线 Parakeet）解决「随时下指令」，通话转录解决「会上不漏事」。

**第四，多平台用两条技术栈实现。** 原生部分 Swift 6 + SwiftUI，其余用 Tauri 2。**刘海 / 动态岛这类深度依赖系统 API 的平台，原生是唯一选择；通用 UI 上跨平台方案更经济。** 这是务实的分工，不是技术洁癖。

**第五，它明确选择了「可用」而不是「好看」。** 作者的动机段落说明了这个市场的问题：漂亮但装不上、装不上就没人用。**在工具类项目上，能装、能用、能常驻，优先级高于视觉完成度。**

## 后续发展建议

**Coucou 提供的最重要启示是：审批入口的「形态」比审批逻辑本身更影响采用率。**

- **内部平台做「人在环内」时，通知通道的形态要当成一级设计项。** 常见做法是：Agent 卡住 → 发一条企业 IM → 人点进机器人 → 再点确认。**这条路要跨两层界面，摩擦足以让人干脆不接。** 更现实的形态是：**在 IM 里直接给出可执行选项（允许一次 / 允许本次任务 / 拒绝并说明）**，让审批就地完成。Coucou 只是把这件事推到极致，但**「就地审批」这个原则可以低成本落地**。
- **审批的信息量要够做决定。** 一个只有「同意 / 拒绝」的弹窗，会让人习惯性盲点。**建议审批卡片至少带上三件事：这个 Agent 要做什么、涉及哪些路径或系统、权限边界是什么**——这直接决定了人是被迫盲批还是能真的判断。
- **审批的可信度是安全问题，不是体验问题。** Coucou 这类产品的形态意味着「谁能批」这件事必须在服务端有强绑定——**一旦本地状态可被伪造或劫持，权限边界就破了**。README 没有展开这部分，**这是同类产品最关键也最少被讲清楚的一面**，内部平台落地时必须自己补上：审批请求要带不可伪造的身份与会话绑定，且服务端留审计。
- **优先级建议：高优先级通知 + 低频深度交互，可以分开做。** 像 Coucou 这样把常驻组件做到极致，体验上限高但工程重。**内部平台可以先用「IM 内就地审批」拿到 80% 的收益**，再针对少数高频场景做常驻形态。

**风险与局限**：v0.5.3 早期，493 个 open issue 配 6,456 star，issue 密度偏高；Swift 6 + SwiftUI + Tauri 2 混合栈，跨平台一致性要额外维护，**Mac 刘海交互在 Windows / Linux 退化为「屏幕顶部」**；功能上依赖对 Claude Code 等 CLI 会话的检测，会跟着上游 CLI 变化失效；作者保留名称、Mochi 形象和音效版权，代码 MIT——采用时注意区分。
