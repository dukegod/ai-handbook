# Nutlope/hallmark：Floor / Reflex / Finish 三档 gate，把审美接进流水线

> **TL;DR**：45,069 star、**周涨星 +11,566（涨星/存量 25.7%）**。hallmark 由 Together AI 做的设计 skill，核心不是 50 套主题，是**把 gate 分成三档**：**Floor 永不发布**（对比度、焦点、减弱动效、捏造事实、手机布局崩坏）、**Reflex 是模型默认会犯的毛病**（有理由可以推翻，但**必须留记录**）、**Finish 是打磨细节，永不阻塞发布**。**这是把「主观审美」变成「可执行、可记录、可推翻的检查项」的最完整一次尝试。**

📅 数据窗口：2026-10-26 ~ 2026-11-02 ｜ 🏷️ Harness 规则化 ｜ 本周涨星 +11,566 ｜ 总 star 45,069

## 是什么

[Nutlope/hallmark](https://github.com/Nutlope/hallmark) 定位为「**一个拒绝看起来像 AI 生成的设计 skill**」，支持 Claude Code、Codex、Cursor、OpenCode。

它盯的是「读起来像机器做的」的具体迹象，README 的例子很具体：**每个标题上都有 eyebrow 引导词、字母加宽的大写标签、标题里恰好一个彩色词、整页空框架或只有照片、hero 区撑不满首屏、每页结尾都放邮件订阅、表单只显示「谢谢」却什么都没发**。

## 技术亮点

**第一，三档 gate 是整份设计里最值得抄的部分。**

| 档位 | 含义 | 能否推翻 |
| --- | --- | --- |
| **Floor** | 对比度、焦点、减弱动效、捏造事实、布局破损 | **永不发布** |
| **Reflex** | 模型默认会陷入的毛病（eyebrow、大写标签、彩色词……） | **可推翻，但须留理由** |
| **Finish** | 工艺细节（阴影、圆角、字距之类） | 永不阻塞发布 |

**这个分级的本质是按「推翻成本」而不是按「问题严重度」分类。** Floor 是安全问题（推翻了就是缺陷），Reflex 是审美问题（允许有理由地偏离），Finish 是锦上添花（不该拦住交付）。**内部平台的 lint 规则体系可以用这套分级重排**——现在很多规则集只有「全部 error」或「全部 warn」两档，缺了中间那档「**记录后可推翻**」。

**第二，Reflex 的「留记录」让推翻变成资产。** 推翻一次不是消失，而是留下一条「模型为什么这么判断」的记录。**这些记录累积起来就是团队的设计偏好档案**——比让人写一份设计规范有用，因为它是从真实产出里长出来的。

**第三，主题是「材料」不是「方案」。** README 原文：**「一个主题是材料，不是一份计划：它从不说页面该有什么内容、什么顺序，所以同一个主题下两个提示词会做出两个不同的页面。」** 50 个主题每个是一个不超过 8 KB 的文件，配一张成品页截图，构建时**只读一个主题文件**。这避免了主题变成模板——**模板会让所有页面长得一样，正是「AI 味」的根源之一。**

**第四，构建流程里有一次真正的冷评审。** 四步：预检读取项目（字体、配色、框架、锁定的 `design.md`）并**只问一次**要什么素材；`theme.mjs deal` 发三个主题、`draw` 从页面「要完成的事」推导骨架；**hero 单独先建、渲染出来冷评审一遍，然后其余页面才开始存在**；最后 `sloplint.mjs --render` 在八个宽度下检查，再由 subagent 用全新视角复核。

**第五，改版模式带完整性校验。** `/hallmark redesign <path>` 保留内容和接线、只换系统和布局；`sloplint --before` **先记录每个链接、字段、处理器和标题**，`--kept` 在改版后**校验没丢东西**，交付物是前后并排对比。`/hallmark audit <path>` 只报告不改。

**第六，安装方式本身是跨 harness 的样本。** `npx skills add nutlope/hallmark -g` 一条命令装到所有项目，也可 `--agent claude-code` 指定单一 harness，或作为 Claude Code 插件 `/plugin marketplace add nutlope/hallmark` 安装。

## 后续发展建议

**hallmark 证明了一件事：AI 味不是审美问题，是缺少可执行判定标准的问题。** 四个判断：

- **三档 gate 应该成为内部平台 lint 规则的分级标准，替换现有的 error / warn 二分。** 建议：**Floor = 不可推翻的质量底线**（正确性、可访问性、数据真实性）；**Reflex = 默认行为，可推翻但留痕**（风格、布局、措辞）；**Finish = 建议，永不拦截**。**价值在于把「Agent 违反团队偏好」和「Agent 犯了 bug」在工具层面分开**——混在一起就是要么全放开要么全拦死。
- **「推翻必须留记录」是真正的杀手锏，建议优先落地。** 内部平台的 Agent 质量记录通常只有「pass / fail」。**加上「以什么理由推翻了哪条规则」，你就有了团队偏好数据**——这是自建平台独有的、外部工具给不了的。
- **「主题是材料不是方案」可以迁移到内部的知识 / 提示词资产上。** 很多团队的提示词库退化成模板库，结果是所有产出长得一样。**建议区分「材料层」（素材、约束、词汇）和「方案层」（结构、顺序、字段），默认只用材料层。** 它和上期 `impeccable` 值得一起看——后者是 62 条确定性规则，方向相反但不矛盾。
- **「hero 单独先建 + 冷评审」的顺序值得抄。** 全量生成完再评审，成本高且容易变成走过场。**先做一块、评审、再做下一块**，能把质量前移。内部平台做生成物自动评审时，**分块推进 + 每块独立评审**通常比整体评审更有效。

**风险与局限**：**没有 release**（GitHub API 返回 404），版本只能跟 git 走；45,069 star 对应 75 个 open issue（0.17%），比例健康，但**自 2026-04-27 建仓以来只有 2026-10-29 一次 push**，**维护节奏并不密**——**更像设计良好的静态产物，而不是持续演进的工程项目**。浏览器类检查（`sloplint --render`、截图）**还需额外装 `puppeteer-core` 和 Chrome**，缺了只能跑静态检查——**最严格那档检查在很多环境下会静默降级**。README 也承认它**受启发于** `impeccable`、`taste-skill`、`frontend-design` 等一堆同类项目——**这个赛道已经很拥挤，差异主要在机制（分档 gate + 主题材料化）而不是覆盖面**。
