# mksglu/context-mode：把上下文成本变成可工程化的指标

> **TL;DR**：context-mode 是个 MCP 服务器，用「工具输出沙箱化」把原始数据挡在上下文窗口外（315 KB → 5.4 KB，98% 缩减），再用 SQLite + FTS5 保住会话连续性。本周 +3,556，但它是本周最该被认真读的仓库。

📅 数据窗口：2026-10-15 ~ 2026-10-21 ｜ 🏷️ 上下文工程 / Agent 基础设施 ｜ 最新 release：`v1.0.169`（2026-06-29）

## 是什么

它解决的问题描述得很具体：每次 MCP 工具调用都把原始数据直接灌进上下文窗口——一次 Playwright 快照 56 KB，20 条 GitHub issue 59 KB，一份访问日志 45 KB。30 分钟后 40% 的上下文没了；等 Agent 被迫压缩对话来腾空间，它会忘掉自己刚在编辑哪些文件、有哪些任务在进行、你最后问了什么。

三个解法：

1. **Context Saving** —— 沙箱化工具输出，315 KB 变 5.4 KB。
2. **Session Continuity** —— 每次文件编辑、git 操作、任务、报错、用户决策都记进 SQLite；对话被压缩时不回灌全文，而是索引成 FTS5 条目，用 BM25 检索相关部分。不带 `--continue` 启动则立刻删掉上个会话数据。
3. **Think in Code** —— LLM 应该**写程序做分析**，而不是把 50 个文件读进上下文再数函数。Agent 写一段脚本完成统计，只把结果 `console.log` 出来。一个脚本替代十次工具调用。

## 技术亮点

它的 benchmark 表是说服力最强的部分：

| 场景 | 原始 | 进上下文 | 节省 |
| --- | ---: | ---: | ---: |
| Playwright 快照 | 56.2 KB | 299 B | 99% |
| GitHub Issues（20 条） | 58.9 KB | 1.1 KB | 98% |
| 访问日志（500 请求） | 45.1 KB | 155 B | 100% |
| 分析 CSV（500 行） | 85.5 KB | 222 B | 100% |
| Git log（153 commits） | 11.6 KB | 107 B | 99% |
| 子 Agent 仓库调研 | 986 KB | 62 KB | 94% |

整套会话下来，315 KB 原始输出变成 5.4 KB，**会话时长从约 30 分钟拉到约 3 小时**。内部机制上，检索用了 Reciprocal Rank Fusion + Proximity Reranking + 模糊纠错，配合 TTL 缓存与渐进式限流。

## 后续发展建议

**这一条最值得记住：「上下文」正在从「模型的限制」变成「团队的预算」。** 过去我们优化上下文是为了让模型别崩；现在优化上下文直接影响**会话时长、token 成本、以及 Agent 能承载的任务复杂度**。3 小时 vs 30 分钟，这个差距不是体验优化，是能不能做长任务的门槛。

我的三个判断：

- **「Think in Code」会从某个工具的卖点变成通用工程规范。** 「让 LLM 写代码做统计，而不是读数据做统计」这条原则，适用范围远超编码 Agent。任何把大块数据喂给模型的地方都该重写成「生成程序 + 返回结果」。这与 [AI Native 方法论](../../../ai-harness/index.md) 里的资产飞轮是同一套思路的两种形态。
- **会话记忆外置会与 Agent Memory 赛道合流。** context-mode 用 SQLite + BM25 做「本项目的操作记忆」，Hindsight（本周 +28,261）做「跨会话的长期记忆」，两者解决的是相邻问题的不同层。未来很可能出现统一抽象：短期工作记忆 + 长期事实记忆由同一个记忆层提供，区别只是保留期与检索策略。
- **风险：这是一个「反向约束」的思路，可能与模型能力提升互相抵消。** 如果上下文窗口和压缩质量继续提升（1M 上下文已经不是新闻），98% 缩减的价值会下降。项目的长期护城河不在压缩率，而在于**它顺手建立起来的「会话操作日志」**——那是一份结构化的、跨工具的、机器可读的项目工作记录，比原始对话历史更有价值。建议关注它是否往这个方向深化。

**注意**：它支持 17 个客户端与 OpenClaw gateway，跨 harness 支持面很广，这说明「上下文工程」正在成为**跨 harness 的公共层需求**，而不是某个客户端的特性。
