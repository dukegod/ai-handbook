# HKUDS/CLI-Anything：把任意软件变成 Agent 可调用的 CLI

> **TL;DR**：CLI-Anything 主张 CLI 是人和 Agent 之间**通用接口**，并提供一条 7 阶段流水线把任意软件（含 GIMP 这类图形界面软件）转成 Agent 可调用的 CLI。本月涨星 +6,135、总 star 55,721。

📅 数据窗口：2026-10-15 ~ 2026-10-21 ｜ 🏷️ 工具接入 / Agent-Native

## 是什么

[CLI-Anything](https://github.com/HKUDS/CLI-Anything) 的核心命题写在「Why CLI?」一节，理由有六条：

- **结构化且可组合** —— 文本命令天然匹配 LLM 的输入格式，也能串联成复杂工作流
- **轻量且通用** —— 开销极小，跨系统工作，不依赖重型运行时
- **自描述** —— `--help` 本身就是文档，Agent 可以自己发现用法
- **已被验证** —— Claude Code 每天通过 CLI 跑成千上万条真实工作流
- **Agent 优先设计** —— 结构化 JSON 输出消除解析复杂度
- **确定且可靠** —— 结果一致，Agent 行为可预测

它提供 CLI-Hub 形态的仓库市场，实际用法是给 Agent 装一个插件，然后 `/cli-anything <软件路径或仓库>`，由 Agent 分析软件并**生成一整套 CLI**（README 里以 GIMP 为例，走完全部 7 个阶段）。生成后可以继续做**广度精修**（分析各能力之间的缺口）或**聚焦精修**（针对某个特定功能区域）。产物既可以 clone 仓库，也可以直接复制到 Claude Code 的插件目录、装成 Pi 的扩展。

安装路径覆盖多种 Agent 平台：Claude Code 的插件市场（`/cli-anything`）、Codex、Cursor 等，各平台有对应的插件目录与重载方式。

## 技术亮点

**「让 Agent 生成 CLI，而不是让 Agent 直接调 GUI」是这里最重要的思路。** 传统做法是给 Agent 一个 GUI 自动化工具（Playwright 那类）——但 GUI 是给**人眼**设计的，Agent 看到的是无结构的像素和控件树，语义稀薄且脆。**把软件转成 CLI，等于给 Agent 造了一个语义明确的接口层。** 本周另一个深读提到的 [REA](./rea.md)（逆向二进制）其实是这条路的极端版本：连闭源二进制的语义都要挖出来。

**「7 个阶段」这个流程化设计，说明它把「软件 Agent-Native 化」当成可复用的工程流程，而不是一次性 hack。** 流程化的价值在于每一步的产物都可检查——这与 REA 的「证据优先」契约是同一个思路：**宁可多花一步把语义显式化，也不要让模型在模糊的界面上猜。**

## 后续发展建议

**CLI 作为 Agent 接口层的地位已经很稳固了，但「谁来维护生成的 CLI」是个悬而未决的问题。**

三个判断：

- **这条路的终局可能是「CLI 不再需要人工维护」。** 如果 Agent 能从 GUI 软件生成 CLI，那它也能从 CLI 反向生成更高层的语义 API。**真正的终局是「按需生成的能力层」**：Agent 遇到一个没接好的软件，现场生成接口、用完即弃。这比维护一个庞大的 CLI 市场更可持续——市场里每个 CLI 都会腐烂，而现场生成的只活几分钟。
- **成本被低估了。** README 里的「7 个阶段」和「广度精修 / 聚焦精修」暗示生成质量并不一次到位。对**行为复杂的软件**（GIMP 有几百个功能），生成的 CLI 覆盖度、边界条件、错误处理都很难保证。**建议评估时挑一个功能边界清晰的目标软件先试**，别拿最大的那个上手。
- **与 MCP 的关系需要想清楚。** MCP 是「工具」协议（工具怎么被描述和调用），CLI 是「接口」形态（工具的接口长什么样）。两者不冲突，但**CLI 天然更适配 Agent 的文本推理优势**，且不需要额外协议层就能被任何 harness 使用。**MCP 适合云端服务，CLI 适合本地软件**——这个分工线在企业内网场景里尤其清晰（本地软件本来也不该出网）。

**对内部团队的启示**：内部有大量只暴露 GUI 或私有协议的内部系统。**CLI-Anything 的思路提供了一个可行的路线：先让 Agent 生成一个内部 CLI 层，再基于它接 MCP。** 这比逐个系统手工写 MCP server 便宜得多。
