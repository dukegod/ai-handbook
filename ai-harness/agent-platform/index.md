# AI 研发 Agent 平台：定位与边界

> **TL;DR**：平台组织任务、能力与证据，不自动产生自交付能力。

> **理论草案**：本文提出平台的职责划分，不描述已实现产品或统一标准。

## 为什么是 AI 研发 Agent 平台

本文把 AI 研发 Agent 平台定义为组织项目、任务、Agent、工具、产物和证据的承载与治理系统。范围可以覆盖编码，也可以延伸到需求、设计、验证和运行协作，因此采用“研发”而非仅“编码”的名称。

这是概念范围，不要求一个平台同时具备全部能力。共享界面只是入口；任务边界、实际状态和决定依据是否清楚，才决定它承载了什么工作。

## 与前三条主线的关系

| 主题 | 向平台提出的需求 | 平台不能代替的内容 |
| --- | --- | --- |
| AI coding | 提供任务上下文、工具和变更查看 | 编码与验证本身的正确性 |
| AI Native | 表达角色、契约、知识和质量约束 | 团队对目标和规则的责任 |
| AI 自交付 | 连接阶段、决定、产物、证据与反馈 | 验收判断和真实价值效果 |

平台可以只服务编码任务，也可以承载完整交付。它不是必然位于自交付之后的成熟度等级；是否形成交付闭环，需要另外判断。

## 以交付事项组织信息

用户应能围绕同一事项理解：为何做、当前处于什么状态、依据是什么、下一步是什么、需要谁决定。对话、任务、文件和报告可以作为不同视图，但不能各自维护相互冲突的进度。

以搜索改进为例，平台应关联需求版本、查询实现、权限验证和发布决定。一个聊天窗口显示“完成”，不足以替代上述对象及其实际结果。

## 人的判断与接管

平台应区分建议、已授权动作、实际执行结果与待审决定。遇到阻塞时，呈现缺失条件、影响、可选处理方式和已有证据，使人能够作出具体决定。

暂停、继续或接管需要保持上下文和责任连续性。人点击接受不能让未运行的测试变成通过；工具连接成功也不能扩展授权范围。

## 边界与成本

统一承载可以减少信息分散，但也可能增加配置、维护与协作成本。是否值得平台化属于效果假设，应结合使用范围判断。本文不规定技术栈、部署形式或产品选型。
