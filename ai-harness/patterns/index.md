## 从任务到可检查的变更

这里采用工作定义：AI coding 是 AI 参与理解、实现、调试和验证编码任务的工作方式。任务可由人逐步组织，也可在已确定范围内交由 Agent 连续推进；自动执行程度不改变检查结果的责任。

| 环节 | 需要明确的内容 | 不能替代的判断 |
| --- | --- | --- |
| 理解与上下文 | 目标、现有行为、相关代码、约束和未知 | 历史代码不自动等于当前需求 |
| 任务拆分 | 输入、修改范围、依赖和验收 | 清单完整不代表范围正确 |
| 实现与集成 | 变更及其对现有行为的影响 | 代码存在不等于功能成立 |
| 诊断与修正 | 现象、可检验的原因假设和修复依据 | 反复重试不等于定位根因 |
| 测试与审阅 | 预期、实际结果、覆盖范围与剩余风险 | 测试通过不等于没有缺陷 |

这些责任可以反复交替，无需每次形成固定的串行手续。

## 三个已有模式

| 场景 | 阅读入口 |
| --- | --- |
| 调整代码结构，保持约定行为 | [代码重构模式](./refactor) |
| 用测试表达预期并观察结果 | [测试生成模式](./testing) |
| 解释接口、使用方式与维护边界 | [文档生成模式](./documentation) |

例如重构搜索函数，应先明确哪些查询行为必须保持，再围绕差异检查。AI 生成更多测试，不必然增加有效覆盖；文档描述同样需要与实际行为核对。

## 与后续主题的关系

一次任务可以依靠临时整理的上下文完成。AI Native 进一步讨论如何让上下文、契约、工程结构和质量机制成为持续可用的研发条件。

AI 自交付扩展到目标、设计、验收、授权和运行反馈。编码任务只是其中一类工作，代码完成不自动覆盖产品接受与发布责任。
